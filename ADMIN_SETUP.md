# Аккаунт владельца и вход по юзернейму

## Администратор — ваш настоящий аккаунт, не общий демо-логин

1. Повторно выполните `supabase-platform-schema.sql` в SQL Editor своего проекта.
2. Зарегистрируйте свой аккаунт `cnizroman` с собственной почтой и паролем.
   Если он уже существует, используйте его, не создавайте новый. Подтвердите
   email по письму (Confirm email должен быть включён в Auth).
3. В Supabase → Authentication → Users найдите **именно свою почту** и скопируйте
   свой User UID. Не ориентируйтесь только на юзернейм: в старой версии проекта
   он автоматически выдавал привилегии. Новый код этого не делает.
4. В **SQL Editor**, не в браузерной консоли, выполните следующий запрос,
   заменив `<ВАШ USER UID>` настоящим UUID:

```sql
update public.profiles
set role = 'admin', is_founder = true,
    badges = array['Основатель платформы', 'Администратор']
where id = '<ВАШ USER UID>'::uuid and username = 'cnizroman';
```

5. Перезагрузите сайт и войдите. Все шесть встроенных текстов и цикл привяжутся
   к этому аккаунту; в студии появится **«♛ Админ-панель»**. Там выдаются и
   отзываются произвольные значки/достижения. Чужие произведения не появляются
   в разделе «Мои произведения» даже у администратора.

Если по старой версии были выданы посторонние админские права, проверьте
`select id, username, role, is_founder from public.profiles;` и вручную отзовите
их у проверенных посторонних UUID. Миграция намеренно не отнимает права у
существующего владельца вслепую.

Ни фронтенд, ни юзернейм, ни регистрационные метаданные не могут назначать
роль, основателя или самостоятельно выдавать значки. Проверка находится и
в JS, и в триггере PostgreSQL. Локальный `cnizroman / demo1234` — только
браузерный режим без серверных прав; при подключении Supabase такая сессия
сбрасывается. Для реального аккаунта используйте собственный пароль.

## Вход по юзернейму в Supabase

Supabase Auth принимает почту, а не юзернейм. Чтобы не публиковать почту
каждого автора в открытой таблице, добавлена серверная Edge Function:
`supabase/functions/username-login/index.ts`.

Разверните её в своём Supabase проекте:

```sh
supabase functions deploy username-login --no-verify-jwt
```

Стандартные `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`
доступны только серверной функции. **Не копируйте service role в сайт или чат.**
В функции используйте лимиты Supabase Auth; для публичного запуска также
настройте лимит запросов на шлюзе/защиту от перебора. Пароли не логируются.
Ошибки для отсутствующего юзернейма и неверного пароля одинаковы.

До развёртывания функции можно войти по email в том же поле. В локальном
режиме вход по юзернейму работает сразу и не требует функции.

## Файлы и социальные подключения

Полный обновлённый SQL создаёт `profile-media` и Storage RLS. Провайдеры OAuth
и Manual Identity Linking настраиваются отдельно; подробная инструкция —
[SOCIAL_AND_MEDIA_SETUP.md](SOCIAL_AND_MEDIA_SETUP.md). Привязка соцсети
никогда не назначает роль администратора.
