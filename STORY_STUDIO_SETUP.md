# Новая мастерская: включение на настоящем сайте

## Один шаг в базе

В этой ветке подготовлен **`STORY_STUDIO_SETUP.sql`**. Это один файл для SQL Editor существующего проекта платформы. Он включает ручную премодерацию и новые настройки мастерской. Отдельно запускать старую миграцию модерации не нужно. Повторный запуск допустим.

1. Откройте https://supabase.com/dashboard/project/ydxnhdbuxjrrpypkgkee/sql/new.
2. Скопируйте **весь** `STORY_STUDIO_SETUP.sql`, от первого `begin;` до последнего `commit;`, и нажмите **Run**. Не запускайте отдельные выделенные строки.
3. После успешного выполнения перезагрузите сайт. Клиент заново проверит наличие серверных функций.

Скрипт рассчитан на уже установленную базовую схему платформы. Он не создаёт новый проект и не меняет пароли аккаунтов, роли пользователей, email confirmation или настройки OAuth.

**Агент не применял этот SQL к реальному проекту:** интеграция Supabase в разговоре выключена. Положительные SQL-тесты — локальные проверки PostgreSQL-совместимой базы, не подтверждение активации на настоящем сервере.

## Что доступно без новой SQL-настройки

- Кнопка `◐` в шапке: пять личных тем сайта. Пресеты применяются и сохраняются сразу, в том числе для гостя. Аккаунты и гость имеют отдельные настройки в этом браузере.
- В профиле больше нет полей «Акцентный цвет» и «Цвет обложки». Существующие значения оформления не стираются при обычном сохранении.
- Подсказки регистрации и предупреждение о неизменяемом юзернейме.
- Визуальное редактирование и новые безопасные блоки текста.
- Локальный режим поддерживает оформление историй, но **не выдаёт локальный пароль за настоящую защиту**.

Сохранение нового авторского стиля в общую базу и установка пароля требуют SQL. До настройки серверная парольная кнопка отключена, а несохранённый новый стиль не выдаётся за сохранённый.

## Куда нажимать

**Студия автора → Мои произведения → нужная история.**

- **«Доступ к истории»**: установить отдельный пароль (дважды), заменить или снять. Сначала создайте карточку истории; настройки доступа находятся на её странице в мастерской. Пароль может назначить любой автор своей истории, не только администратор.
- **«Карточка произведения → Авторское оформление»**: выбрать один из шести стилей, шрифт, размер букв, интервал, ширину страницы, выравнивание, буквицу, вид заголовков и разделителей.
- **«Новая глава»**: обычное визуальное поле, кнопки оформления, вставка блоков через диалог. В блок можно кликнуть и переместить его выше/ниже или удалить; отмена возвращает удалённое. Текст и заголовки блоков редактируются прямо на странице.
- **«Оформление для читателей»** в редакторе главы: тот же конструктор. Изменения стиля сохраняются при сохранении главы. Если сохранение стиля прошло, но запрос главы затем завершился ошибкой, стиль уже изменён, а текст остаётся в локальной резервной копии; общего транзакционного сохранения двух запросов нет.
- **«Настройки рабочего места»**: личный шрифт редактора, вид областей, ширина, орфография, цель. Они не меняют авторский стиль книги.
- **«Разметка»**: дополнительный режим для точной работы с исходным текстом, поиска/замены, импорта и шаблонов. При работе с этими инструментами редактор переключается в разметку. Цвет текста и выделения работает и в визуальном режиме.

В читалке по умолчанию используется авторский стиль. Кнопки «Тьма / Бумага / Свет» позволяют посетителю поменять цвета для себя; «Авторская» возвращает задумку автора. Собственный размер чтения также сохраняется отдельно.

## Что именно защищает пароль

- В базе находится bcrypt-хеш в закрытой схеме `ink_private`; хеши не возвращаются клиентам.
- Публичный REST-доступ к строкам закрытых глав запрещён RLS. `publication_snapshot()` также их не выдаёт.
- Текст доступен читателю только через серверную проверку пароля; название, обложка, аннотация, автор и факт защиты публичны.
- Сайт не сохраняет введённый читателем пароль. Разрешённый текст держится в памяти текущей вкладки, не попадает в публичный localStorage-кеш. Перезагрузка требует повторного ввода; UI-доступ в памяти ограничен 15 минутами/версией произведения и сбрасывается при выходе.
- Это **не DRM**: уже полученный текст можно скопировать или скачать, его нельзя отозвать, в том числе после смены пароля. Локальные черновики и JSON-копии самого автора содержат его текст и заметки открыто — храните их соответственно.
- Ограничение пароля: минимум 8 символов, максимум 72 байта UTF-8 (ограничение bcrypt). Старый пароль нельзя посмотреть, только заменить.
- Сервер допускает до 60 неуспешных проверок за 5 минут **на произведение в целом**, не на IP. Успех сбрасывает счётчик. При исчерпании лимита нужно дождаться окна; даже верный пароль до этого будет отклоняться. Для большого публичного трафика стоит добавить внешний антибот/персональные лимиты: общий лимит допускает временную блокировку доступа чужими попытками, но не выдачу текста.
- Автор читает свои черновики, администратор видит текст для проверки без пароля. Изменение стиля или включение/снятие пароля может вернуть чужую историю в черновик; её необходимо снова отправить на проверку. Замена существующего пароля не заменяет проверки содержимого.

**Существующие отдельные HTML-книги владельца не перенесены в базу.** Этот SQL не закрывает их исходники и не превращает старые браузерные парольные окна в серверную защиту. Новая защита относится к историям с главами, созданным через платформу. Произвольные HTML, JavaScript, внешние скрипты и пользовательский CSS не исполняются: сходный книжный дизайн собирается безопасными средствами редактора.

## Техническая проверка

- `npm ci`
- `npm test`
- `npm run test:sql` — базовая схема, модерация, новая защита с настоящим pgcrypto/bcrypt; проверяет и целый файл `STORY_STUDIO_SETUP.sql` дважды.
- Для браузерных тестов поднимите статический сервер на порту 8000 и выполните `npm run test:browser`. Пример: `python -m http.server 8000 --bind 0.0.0.0`. Проверки сети в браузере используют тестовые HTTP-ответы, не настоящий проект Supabase.

Канонические миграции: `supabase/migrations/20261102000200_manual_publication_review.sql` и `20261102000300_story_design_passwords.sql`. `STORY_STUDIO_SETUP.sql` объединяет их в одну транзакцию; при изменении миграций синхронизируйте общий файл. Политики чтения в базовой схеме и старой миграции также сохраняют парольную защиту при повторном применении.

## Обновление дизайна v2

Текущий общий `STORY_STUDIO_SETUP.sql` уже включает миграцию `20261102000400_story_design_v2.sql` последней. Он устанавливает `story_studio_version() = 2`. Если модерация и пароли уже работают, достаточно **STORY_DESIGN_UPGRADE.sql**; не нужно заново настраивать администратора, вход или пароль. Обновление меняет только валидатор оформления и сигнал версии. Старые стили и `{}` остаются допустимы.

Подробнее: [STORY_DESIGN.md](STORY_DESIGN.md). Рабочий проект уже обновлён агентом после тестов и публикации совместимого фронтенда: версия мастерской `2`, модерации `1`. Владельцу повторно запускать SQL не требуется. Проверки и результат — в `DEPLOYMENT_STATUS.md`. Для самостоятельных новых установок открывайте Supabase Dashboard → проект → SQL Editor → New query → вставьте **весь** выбранный актуальный файл → Run. Проверка: `select public.story_studio_version();` должна вернуть `2`. Не запускайте старую миграцию v1 отдельно после v2.
